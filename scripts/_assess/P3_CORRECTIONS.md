# Phase 3 — what the assessment found, and what was done about each finding

Three assessors read the code of release 0.3.0 requirement by requirement (parts A, B and C) and reported
defects beside the statuses they recorded. This file lists every finding and what happened to it. It is the
source for the section "Defects found and corrected" of `docs/NUMERO_IMPLEMENTATION_STATUS.md`, and it tells a
person who re-reads a status file which facts changed after the status was first written.

State after the corrections: database migration pieces `p3_01 … p3_27` applied; local files
`supabase/migrations/0014 … 0019` re-extracted from what the database holds.

## A fault made while correcting, and found by the tests

The correction C4 (p3_24) rewrote `numero_private.notify_holders` from the text of the migration file, where the
function still named the column `profiles.is_group_admin`. An earlier correction (p3_13) had renamed it to
`is_group_super_admin` in the database. Because a notice must never stop an approval, the trigger swallowed the
error, and **no notice of an approval or of an alert was written** between p3_24 and p3_25. The database suite
found it at once (T240, T241, T253, T276 and T277 failed); p3_25 corrects the column. The database held no
company and no user at the time, so no notice was lost. The lesson is recorded: a function is rewritten from its
live text (`pg_get_functiondef`), never from a file.

The same run reported T187 as failed. That was a fault of the test file, not of the database: a block added
before it left the role of a signed-in person set, so the attempt to delete stock movements matched no row under
row level security and raised nothing. The block now ends by resetting the role.

## Not corrected, and why

* **1899 Dynamic reality, 1826 Clone department, 1886 Department customisation, 571 Manufacturing** are not
  built. They stay PLANNED in the ledger.
* **The live data layer has no automated test.** Every rule is tested in the database (SQL suites) and in the
  sample engine (application tests); the code between the screens and the database (`src/api/supabase*.ts`) is
  type-checked only, and no screen has been driven against the live database.
